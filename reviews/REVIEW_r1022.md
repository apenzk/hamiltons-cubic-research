## Item 2: `isWeyl_smul_op` against `isWeyl_smul`. CONFIRMED

`#check` gives two different statements, so the docstring's distinction is real:

- `isWeyl_smul : IsWeyl R → ∀ (c : ℝ) {X}, IsSkew X → R (c • X) = c • R X`, homogeneity of a fixed `R` along its argument.
- `isWeyl_smul_op : IsWeyl R → ∀ (c : ℝ), IsWeyl (c • R)`, closure of the predicate under scaling the operator.

**`θ = 0` is covered and the docstring describes it accurately.** *`idemOf W 0 = 0` as a function, which the kernel confirms by `funext X; simp [idemOf]`, and `isWeyl_idemOf hW 0` type-checks.* The docstring's "at every `θ`, `θ = 0` included, where it is the zero operator" is exact.

**One sentence in the same docstring claims more than the declaration gives.** "THIS IS WHAT CARRIES ANY STATEMENT ABOUT A RECORD-WEYL OPERATOR TO `idemOf W θ`" holds for statements hypothesised on `IsWeyl`. A statement hypothesised on `IsWeylOp` needs the linearity clause carried too, which is [IsLinOp.smul](../lean/HamiltonsCubic/Base/FoxProduct.lean) and [isLinOp_idemOf](../lean/HamiltonsCubic/Base/FoxProduct.lean), both of which predate this commit. The claim is true in effect and overstated as written.

## Item 4: "the operator norm reaches the bound". REFUTED

**The claim covers one of the two halves of `cubicTri`.** `cubicTri X Y Z = innerOp2 (X.comp Y) Z - ½ phiTri X Y Z`, and `ContinuousLinearMap.opNorm_comp_le` with `le_opNorm` do reach the first half. I screened that they apply at this type rather than only in principle: inside the `Matrix.Norms.Frobenius` and `OperatorNorm` scopes, `‖A.comp B‖ ≤ ‖A‖ * ‖B‖` and `‖A x‖ ≤ ‖A‖ * ‖x‖` both elaborate at `CurvOp2 (Fin 3)`, and `‖x‖ = ‖(x : Matrix (Fin 3) (Fin 3) ℝ)‖` on `skewSub` is `rfl`.

**The `Φ` half reaches neither lemma.** *[phiTri](../lean/HamiltonsCubic/Results/PhiTri.lean) is `-(1/4) ∑_{ijkl} ⟨B(brS (A φ_ij) (C φ_kl)), brS φ_ij φ_kl⟩`, and the objects inside are bracket values, not composites of operators.* Bounding it needs a submultiplicativity statement for `brS`, the bracket on `Λ²`, of the shape `‖brS U V‖ ≤ 2‖U‖‖V‖`. **The tree has no norm statement about `brS` at all**, only `brS_add_left`, `brS_add_right` and the two `smul` clauses, which a grep over [Bivectors2.lean](../lean/HamiltonsCubic/Base/Bivectors2.lean) and [PhiTri.lean](../lean/HamiltonsCubic/Results/PhiTri.lean) confirms.

**So the file's "what the estimate actually owes is two things" is short by one.** *The third is the bracket bound, and it is not hard: I screened that it follows in about twelve lines from Mathlib's [Matrix.frobenius_norm_mul](../lean/.lake/packages/mathlib/Mathlib/Analysis/Matrix/Normed.lean), which is the Frobenius norm's submultiplicativity, plus the triangle inequality on `UV - VU`.* Written out, the `Φ` half then carries a constant of its own: each summand is at most `2‖A‖‖B‖‖C‖ ‖φ_ij‖² ‖φ_kl‖²`, so `|phiTri A B C| ≤ 2 n²(n-1)² ‖A‖‖B‖‖C‖` at `n = |ι|`, against `normSq2 id = n(n-1)/2` for the other half. **The correction is to replace "two things" with three and to name the third**, since a recorded debt that omits an item is what kept the last result unattempted for three rounds, by this cycle's own account in [ATTEMPTS.md](../ATTEMPTS.md).

## Item 5: the constant. CONFIRMED, and the two halves compose exactly

The chain, with every step named:

1. `|innerOp2 A B| = |½ ∑_{i,j} ⟨A φ_ij, B φ_ij⟩| ≤ ½ ∑_{i,j} |⟨A φ_ij, B φ_ij⟩|`, the triangle inequality and `innerOp2`'s own `½`.
2. `≤ ½ ∑_{i,j} √⟨Aφ,Aφ⟩ √⟨Bφ,Bφ⟩`, which is `abs_inner2_le`.
3. `= ½ ∑_{i,j} (‖Aφ‖/√2)(‖Bφ‖/√2) = ¼ ∑_{i,j} ‖Aφ_ij‖ ‖Bφ_ij‖`, which is `inner2_self_eq_frobenius` used twice.
4. `≤ ¼ ‖A‖‖B‖ ∑_{i,j} ‖φ_ij‖²`, which is `le_opNorm` used twice.

**And `¼ ∑_{i,j} ‖φ_ij‖²` is literally `normSq2 id`**, since `normSq2 id = ½ ∑_{i,j} ⟨φ_ij, φ_ij⟩ = ½ ∑_{i,j} ‖φ_ij‖²/2`. *So the `½` in `inner2_self_eq_frobenius` and the `½` in `innerOp2`'s ordered-pair doubling compose to the `¼` that is already inside `normSq2 id`, and the parent's `|innerOp2 A B| ≤ ‖A‖‖B‖ · normSq2 id` is exact rather than approximately right.*

**The numerical value agrees with the record.** `phi i j = single j i 1 - single i j 1`, so `‖φ_ij‖² = 2` off the diagonal and `0` on it, giving `∑ ‖φ_ij‖² = 2n(n-1)` and `c = n(n-1)/2`. That is [Bivectors2.lean](../lean/HamiltonsCubic/Base/Bivectors2.lean)'s own `normSq2 id = ½n(n-1)`, and `3` at `Fin 3`, which [r1021](REVIEW_r1021.md) recorded. **No factor is lost anywhere in the chain.**

## Item 6: the library claim. CONFIRMED, the inference from it is not

**The negative claim holds.** `MultilinearMap.continuous_of_finiteDimensional` is an unknown constant in the kernel. No file in Mathlib mentions `FiniteDimensional` and a multilinear map on the same line, [Mathlib/Analysis/Normed/Module/Multilinear/Basic.lean](../lean/.lake/packages/mathlib/Mathlib/Analysis/Normed/Module/Multilinear/Basic.lean) never mentions `FiniteDimensional`, and [Mathlib/Analysis/Normed/Module/FiniteDimension.lean](../lean/.lake/packages/mathlib/Mathlib/Analysis/Normed/Module/FiniteDimension.lean) never mentions a multilinear map. The linear analogue is `LinearMap.continuous_of_finiteDimensional` and the affine one is `AffineMap.continuous_of_finiteDimensional`, with no third.

**What the file draws from it goes further than the fact supports**, in two ways.

- **`LinearMap.mkContinuous₂` is bilinear**, `(f : E →ₛₗ F →ₛₗ G) → (C : ℝ) → (∀ x y, ‖f x y‖ ≤ C‖x‖‖y‖) → E →SL F →SL G`. `cubicTri` is trilinear, so that constructor does not by itself supply the constant the sentence says it supplies.
- **The estimate needs the inequality, not a bundled map.** *What `HasFDerivAt` consumes is `|Pcubic2Quad R H| = o(‖H‖)`, which is a bound on a real number.* Registering `cubicTri` as a `ContinuousMultilinearMap` is one way to get there and is heavier than the alternative of proving the inequality directly, which is the route items 4 and 5 describe. Naming a bundling constructor as what the work must go through makes a choice look like a necessity.

## Item 7: the `IsVonNBounded` decision. REFUTED on one claim, conclusion survives

**The three synthesis claims, checked in the kernel:**

| Claim as recorded | Result |
| --- | --- |
| `NormedAddCommGroup (CurvOp2 (Fin 3) →L[ℝ] ℝ)` fails inside the `OperatorNorm` scope | **Holds.** `failed to synthesize` |
| `IsTopologicalAddGroup (CurvOp2 (Fin 3))` fails inside the scope | **False.** It synthesizes, as `ContinuousLinearMap.topologicalAddGroup` |
| `ContinuousAdd (CurvOp2 (Fin 3))` fails outside the scope | **Holds**, and it fails inside the scope too, so the scope is not what makes it fail |

**The real obstruction is a diamond, and naming it as a missing instance hides it.** *Inside the scope, `#synth TopologicalSpace (CurvOp2 (Fin 3))` returns `ContinuousLinearMap.topologicalSpace`, the native one, while `#synth UniformSpace (CurvOp2 (Fin 3))` returns `PseudoMetricSpace.toUniformSpace`, the one the scoped norm carries.* The topology and the uniformity come from different sources, which is why the dual's normed-group instance cannot be assembled. **This repo has already diagnosed that and named the repair**: [Bivectors2.lean](../lean/HamiltonsCubic/Base/Bivectors2.lean) proposes `toNormedAddCommGroupOfTopology`, which keeps the existing topology, and [lean/INDEX.md](../lean/INDEX.md)'s own `CurvOpInner` row says in this same commit that `TopologicalSpace`, `IsTopologicalAddGroup` and `ContinuousConstSMul` all synthesize through `ContinuousLinearMap`. **That row and [CubicTri.lean](../lean/HamiltonsCubic/Results/CubicTri.lean)'s line contradict each other, and the row is the one the kernel agrees with.**

**The conclusion nonetheless holds.** *Declining to re-promote `IsVonNBounded` is right, and the reason is the one [plan.md](../plan.md) and [ATTEMPTS.md](../ATTEMPTS.md) give rather than the one [CubicTri.lean](../lean/HamiltonsCubic/Results/CubicTri.lean) gives*: the scoped `OperatorNorm` already discharges what `IsLocalMaxOn.hasFDerivWithinAt_nonpos` wants, the constraint set is a set rather than a norm-sphere, and the estimate at issue here is an inequality about real numbers that needs no instance on `CurvOp2` beyond the norm it already has inside the scope. **A failed synthesis is evidence about instances, and this one is evidence about a diamond rather than about whether the inner product should be registered.**
